## 一、核心风险锁定：三类问题 → 本项目风险点映射

上线前测试不追求全量铺开，先按「权限管控、数据泄露」锁定高风险面，再扩散到功能与链路。三类口径（已与用户确认）：

### 1. 越权与权限管控
- 水平越权：居民 A 读取/撤销/标记已读居民 B 的事件（`GET /api/events/{id}`、`POST /api/events/{id}/cancel`、`mark_read`、`reply` 可见性）。
- 垂直越权：居民调用管理员专属接口（`GET/PUT /api/admin/community`、`GET /api/admin/users`、`POST /api/events/{id}/accept`、`reply`）。
- 角色/归属校验缺失：`get_current_user_dependency` vs `get_admin_dependency` 覆盖完整性；注册接口 `role=admin` 拒绝；撤销接口「仅本人」判定。
- 状态机越权：非本人/非对应状态调用 accept/reply/cancel/mark_read 的返回（400/403 语义）。

### 2. 数据泄露（加密 + 密钥 + 暴露面）
- 存储加密：本地 `secure/*.enc` 与云端 `users.json.enc`/`sessions.json.enc` 必须为 AES-256-GCM 密文（已实现，需回归锁定）；密钥 `DATA_ENCRYPTION_KEY` 仅 .env。
- 密钥管理：COS_SECRET_ID/KEY、DATA_ENCRYPTION_KEY 不落文档/日志/知识库/版本库（.gitignore 校验 + 泄漏扫描）。
- 接口/前端暴露：`GET /api/events` 居民端不得返回他人身份证/手机/定位（`list_users` 仅 admin；`event_lat/lng` 仅 admin 返回）；前端错误信息不得回显后端内部异常（堆栈/路径/密钥）。
- 会话泄露：登出后 token 立即失效；token 过期（7 天 TTL）清理；会话表上云后同样加密。

### 3. 注入与滥用
- 参数注入：事件描述/用户名/楼栋房间/回复内容等输入的长度、字符集、SQL/脚本/HTML 注入面（本项目无 SQL，重点为 XSS 与超长输入）。
- LLM 提示注入/语义滥用：事件描述诱导 LLM 改写 event_type/urgency/handler/地址，或绕过无效输入判定（"无效输入/API异常/待审核" 分支）。
- 敏感信息回显：LLM 结果或错误信息中回显身份证号、手机号、内部路径、密钥片段。
- 前端 XSS：回复内容/事件描述渲染是否统一转义（index.html `escapeHtml` 已有，需回归）。

## 二、五步审计流程

### ① 风险排序，锁定高优先级模块
按「越权/数据泄露影响 × 暴露概率」排序：
| 优先级 | 模块 | 理由 |
|---|---|---|
| P0 | 认证与权限（auth.py、main.py 依赖） | 一切越权/泄露的入口 |
| P0 | 事件链路（receive→dispatch→record、超时/失败降级） | 核心业务 + LLM 不可控 |
| P0 | 云存储（cloud_store、AUTH_STORE=cloudbase） | 身份数据上云，加密/密钥即数据安全 |
| P1 | 后台管理（社区设置/用户/受理/回复/撤销） | 管理员面，越权与业务流风险 |
| P2 | 前端交互（index/admin/login 的权限分流、红点、撤销按钮） | 体验与展示层 |
| P2 | geo / 公共工具 | 冒烟级 |

### ② 正常 / 边界 / 异常 三层功能测试
- 正常：居民注册（范围内）→ 登录 → 提交事件 → 派单 → 管理员受理/回复 → 居民查看已读 → 5 分钟撤销；admin 登录直跳后台。
- 边界：注册定位恰好等于半径（≤ 边界允许）、5 分钟撤销临界点（300s±1s）、事件描述 500 字上限、用户名 3/20 位、回复空/1 字、无回复查看。
- 异常：无定位/越界注册、超时撤销、终态撤销、重复撤销、无效输入（问候/闲聊/宠物死亡）、LLM 超时（50s/60s）、云存储对象缺失/网络失败、登录失败（错密码/不存在用户）、token 过期。

### ③ 单元 / 接口 / 业务流 自动回归体系
- 单元：auth（哈希/掩码/TTL）、secure_store（加解密闭环）、cloud_store（fake client）、geo（Haversine/范围内外）。
- 接口：/api/auth/*、/api/events*（含 cancel/mark_read/accept/reply）、/api/admin/* 的 200/400/401/403/404 矩阵。
- 业务流：注册→登录→提交→受理→回复→已读→撤销 端到端（TestClient + LLM mock，不访问真实网络）。
- 统一 runner：见「五、自动化落地」。

### ④ AI 自解释 + 主动造错，识别无效测试
- 每个高风险用例要求「自解释」：标注 目的 / 前置 / 步骤 / 期望 / 反例（为什么这条能抓到缺陷）。
- 主动造错（mutation）抽查：对被测代码做小改动（删一个 `role != "admin"` 判断、改 `>` 为 `>=`、去掉 escapeHtml），断言「测试必须变红」；变不红的用例标记为无效测试并修正或删除。
- 覆盖率护栏：核心模块分支覆盖率 ≥80%；对未覆盖分支列出理由（人工判定可豁免）。

### ⑤ 攻击者视角：八项接口攻防校验（按 OWASP API Security Top 10 拟定）
| # | 攻防项 | 对应 OWASP 2023 | 操作逻辑 |
|---|---|---|---|
| 1 | 水平越权（BOLA） | API1 | 居民 A 用自己 token 访问/撤销/标记已读居民 B 的事件 → 必须 403/404，且不产生副作用 |
| 2 | 垂直越权（BFLA） | API5 | 居民 token 调 admin-only 接口（/api/admin/*、accept、reply）→ 必须 403 |
| 3 | 认证与会话安全 | API2 | 无 token/伪造 token/过期 token/登出后 token 复用 → 401/403；登录错误不区分用户名/密码错误细节 |
| 4 | 对象属性级越权（BOPLA） | API3 | 提交/更新请求携带越权字段（role=admin、他人 user_id、伪造 reviewer 等）→ 被拒绝或忽略 |
| 5 | 资源消耗与限流 | API4 | 高频提交/轮询/注册无限制（当前无限流，需评估加慢速限流或至少记录）；超长输入被拒绝 |
| 6 | SSRF / 外部资源滥用 | API7 | 本项目无用户可控服务端 URL，但需验证：前端高德链接为纯前端拼接、LLM 调用输入不可诱导服务端发起任意请求 |
| 7 | 安全配置错误 | API8 | CORS 收紧、错误信息不泄露堆栈/路径/密钥、默认凭据 admin/admin123456 上线前必须改密、debug 关闭、.env 权限 |
| 8 | 不安全消费外部 API | API10 | LLM 输出被操纵：伪造 is_valid=false/event_type/handler 透传、LLM 返回坏 JSON/空结果必须有降级（硬规则/待审核/处理失败），回复/描述渲染必须转义（防 XSS） |

## 三、测试成本平衡

原则：**保留高价值、合并重复、删除无风险**，避免过度测试拖慢迭代。
- 判定标准：
  - 保留：能捕获 P0/P1 缺陷、覆盖权限/数据泄露/注入面、或回归易碎逻辑（加密、越权、超时降级）的用例。
  - 合并：同一接口同一断言矩阵的不同写法（如各脚本重复的「登录→注册」脚手架）抽到公共 fixture/helper；同一状态机分支多脚本重复覆盖的，归并到统一契约测试。
  - 删除：纯环境性失败（test_geo 与持久化中心配置冲突类的硬编码断言）、与风险无关的复制粘贴用例、造错后无法变红的无效用例。
- 执行：每轮回归按「P0 全量 + P1 关键 + P2 抽样」裁剪；提交前必跑核心集（预计 ≤5 分钟），CI 全量集（预计 ≤15 分钟）。

## 四、链路测试：非模型类线上事故隐患排查

针对「检索未命中、工具调用失败、超时无降级、错误结果直接展示」四类隐患（不归因于模型智商，而归于链路/降级/展示缺陷）：
- 检索未命中：receive 解析失败（地址/类型为空）→ 是否进入「无效输入/待审核」而非直接失败；列表/详情 404 语义是否清晰。
- 工具调用失败：dispatch/record 抛错（LLM API 异常、坏 JSON、字段缺失）→ `_process_event` 异常分支是否置「处理失败」并落盘；是否出现「表面成功、无工单」。
- 超时无降级：语义校验 50s 超时 → 是否降级「待审核」；后台处理 60s 超时 → 是否置「处理超时」；前端轮询 60s 上限后是否有明确提示而非白屏。
- 错误结果直接展示：LLM 返回的 handler/status/回复是否未经校验直接展示（需白名单校验 + 转义）；`error` 字段是否回显给居民（避免内部异常泄漏）。
- 排查方法：故障注入演练（mock 抛错/超时/坏返回，验证降级路径），每条链路至少 1 个「断链用例」纳入回归。

## 五、自动化落地

### 5.1 pytest 化（折中：脚本保持可直接运行）
- 现有 `tests/test_*.py` 独立脚本改造原则：
  - 顶部保留 `os.environ["AUTH_STORE"]="file"` 等环境固定（已普遍具备）；
  - 主体逻辑拆为可被 pytest 收集的函数（`test_*`），`if __name__ == "__main__":` 内保留原「直接运行」入口（`run_all()/main()`），保证 `python tests/test_xxx.py` 仍可单跑；
  - 每个脚本末尾的 `sys.exit(...)` 仅置于 `__main__` 分支，避免 pytest 收集时退出。
- 新增 `tests/conftest.py`：统一固定 `AUTH_STORE=file`、`DATA_ENCRYPTION_KEY`（测试用固定值）、LLM 环境变量；提供「数据隔离」fixture（备份/恢复 data 与 secure，**必须 try/finally 崩溃保护**，修复既有备份丢失事故）；提供公共 helper（注册/登录/建事件/越权 token 对）。
- 统一回归 runner：`scripts/run_tests.py`（或 pytest 默认收集 + `pytest.ini` 配置 core 集与全量集 profile）：
  - `core`：认证/权限/云存储/事件链路/越权攻防（CI 必跑）；
  - `full`：全部用例（含冒烟/前端静态检查）。

### 5.2 GitHub Actions CI 配置要点（`.github/workflows/ci.yml`）
- 触发：push / PR 到 main（或用户指定分支）。
- 步骤：checkout → setup-python（3.12）→ pip install -r requirements.txt → 跑 core 回归（pytest core）→ 跑独立脚本直跑兼容检查（抽样 `python tests/test_auth.py` 等）→ 前端 `node --check`（index/login/admin 内联脚本）→ 密钥泄漏扫描（grep COS_*/DATA_ENCRYPTION_KEY 值不应出现在非 .env 文件）。
- 云端集成测试不进 CI（需真实 COS 凭证），作为「带 secrets 的手动 workflow」或本地放行后执行；CI 内云端相关用例一律用离线 fake client。
- 说明：项目当前为本地仓库；CI 配置先行就绪，待推送到 GitHub 后自动生效。

### 5.3 测试基建修复（前置）
- 备份/恢复 try/finally 崩溃保护；控制台 UTF-8 兼容（emoji 输出）；`tests/run_tests.py` 定位（实时冒烟 vs 回归）与 `pytest.ini` 关系说清；`test_geo` 环境性失败（持久化中心 vs 硬编码默认中心）改为动态取配置。
